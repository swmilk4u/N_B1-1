Part 1. LLM 모델 비교 및 선정 보고서

동일한 "회의록 및 설명 개요 요약" 과업에 대해 3종의 최신 대규모 언어 모델(GPT-5, Claude 4.6, Gemini 2.5 Pro)을 웹(Naito) 인터페이스 환경에서 6개 핵심 평가 축을 기준으로 5점 척도 정량 평가를 실시하였습니다.

1.2 평가 항목 및 기준

비개발자용 교육용 보고서를 설계하는 과업 특성을 반영하여 6가지의 척도로 평가를 세분화하였습니다.

평가 항목 5점 (우수) 3점 (보통) 1점 (미흡)
정확성 (Accuracy) 제시된 원문 정보만 활용, 환각 없음 추측성 정보 1~2개 포함, 대세 지장 없음 허구 정보를 사실처럼 서술 (심각한 환각)
일관성 (Consistency) 재실행 시 양식 및 톤앤매너 100% 동일 반복 실행 시 일부 양식 흐트러짐 동일 질문에 매번 완전히 다른 형태 출력
가독성 (Readability) 쉬운 우리말 표현, 적절한 이모지 및 표 전문용어가 섞여 있으나 대략적 이해 가능 번역체 가득하고 가독성이 현저히 떨어짐
지시문 준수 (Instruction) 목차 범위, 분량 제약 완벽 수행 필수 항목 중 일부 누락되거나 분량 초과 지시 사항을 무시하고 일반 응답 생성
문맥 유지 (Context) 10턴 이상 대화 시 초기 조건 유지 5턴 전후로 조건 망각 시작 다음 턴 질문 시 바로 직전 규칙도 망각
예외 처리 (Exception) 모호한 지시에 되묻고 안전성 확보 의도를 추측하여 무작정 대답함 오작동 또는 비정상적인 답변 반환

1.4 평가 축별 세부 근거 (대화 로그 기반)

  • 정확성: 실시간 정보(오늘 날짜) 등 외부 리소스 부재 시 GPT-5와 Claude는 사실적 오류(환각)를 내지 않고 안전하게 거절하여 Pass 판정을 받았습니다. 반면 Gemini 2.5 Pro는 날짜 정보가 차단된 상태에서도 자의적 억측으로 대답해 3점을 부여했습니다.
  • 일관성: Claude 4.6은 여러 번 반복 생성해도 지정한 용어 변환표와 각 목차의 학습 목표 블록 양식을 흐트러짐 없이 일정하게 출력했습니다.
  • 가독성: Gemini와 Claude는 '게임 세이브 포인트', '마법 복제 종이', '코드 택배' 등 한국어 화자 및 초보자 맞춤형 비유와 한글 순화를 탁월하게 제시했습니다.
  • 지시문 준수: Claude 4.6은 목차 수(8개 고정) 및 이모지 사용 여부를 완벽히 이행했습니다. GPT-5는 다회차 생성 시 목차 수가 9개로 늘어나는 양식 이탈이 관찰되었습니다.
  • 문맥 유지: Claude 4.6과 Gemini는 10턴이 넘어가는 다중 대화 속에서도 턴 3의 '쉬운 말 치환'과 턴 5의 '학습 목표' 등 이전 턴에 정립된 누적 조건들을 끝까지 기억하며 대답했습니다.

📝 최종 선정 결론 (Claude Sonnet 4.6 채택)

비개발자용 교육 자료 설계에 있어 가장 중요한 역량은 "지속적으로 제약 규칙을 누락 없이 유지하는 것(문맥 유지)"과 "지정된 템플릿 양식을 어기지 않는 것(일관성·지시문 준수)"입니다. Claude 4.6은 이 세 가지 지표에서 감점 없이 만점(5점)을 기록하며 종합 점수 28점으로 최종 최적 모델로 채택되었습니다. 10턴 이상의 장기 협업 시나리오에서도 교육 코치 페르소나를 안정적으로 유지했습니다.

Part 2. 프롬프트 시스템 설계 문서

2.1 문제 정의 및 타겟 사용자

  • 문제 상황: GitHub를 처음 쓰는 비개발자는 리포지토리, 커밋, 브랜치 등의 용어에서 심리적 장벽을 느낍니다. 기존 AI의 가이드북 개요는 기술 용어를 그대로 사용하여 사전식으로 딱딱하게 응답하는 한계가 있었습니다.
  • 타겟 사용자: GitHub를 처음 접하는 비개발자 및 코딩 왕초보
  • 과업 목표: 비개발자가 기술적 혐오감 없이 쉽게 시작할 수 있는 맞춤형 학습 로드맵 개요 생성

2.2 입력 템플릿 및 출력 규격

체계적 제어를 위해 아래의 스키마를 고정하여 통제합니다.

입력 템플릿 양식 (Input Schema)
[대상 독자]: GitHub를 처음 접하는 비개발자 [톤]: 친절하고 초보자 친화적 [필수 포함 항목]: GitHub 개념, 리포지토리 생성, 커밋/푸시, 브랜치, PR 기본 [금지 사항]: 전문 용어 과다 사용 금지, 추측성 표현 금지
출력 구성 요소 출력 규격 및 제약 사항
제목 1개 (주제를 명확하고 친밀하게 반영한 한글 제목)
목차 5~8개 (순서가 있는 순차 번호 리스트)
용어 변환표 상단에 고정 (전문 용어 ❌ ➔ 쉬운 표현 ✅ 매핑 테이블 필수)
항목별 설명 각 목차별 1~3문장의 쉬운 설명 제공
학습 목표 각 항목 서두에 1줄 이상의 목표 블록(🎯) 제공 + 마지막에 3개 종합 요약

💡 페르소나 및 시스템 프롬프트 요약 (핵심 원칙)

본 시스템 설계는 과제 미션지에서 제시한 아래의 핵심 페르소나와 3대 원칙을 바탕으로 구성되었습니다.

  • 페르소나: "프로젝트 매니저 출신 업무 자동화 코치" (초보자의 눈높이로 기술을 번역하는 가이드)
  • 3대 핵심 원칙:
    1. 사실/수치/정책은 확인 가능해야 함: 데이터 부재 시 억측 없이 안전하게 차단하거나 '확인 필요' 명시
    2. 부족하면 질문: 입력 데이터가 애매할 경우 자의적 해석을 배제하고 최대 3개까지 되묻기 수행
    3. 최종 출력은 템플릿 준수: 변환표 ➔ 목차 ➔ 학습 목표 스키마를 고정하여 출력

2.3 시스템 프롬프트 (v2 - 최종)

SYSTEM_PROMPT.txt
당신은 "프로젝트 매니저 출신 업무 자동화 코치"입니다. 비개발자 대상 가이드북을 작성할 때 반드시 다음 지침을 지키십시오. 1. **페르소나 규칙**: - 말투는 친절하고 이모지를 적절히 활용하여 독려합니다. - 단 한 단어의 전문 용어도 변환표를 거치지 않고서는 단독으로 사용하지 마십시오. 2. **용어 치환 규칙**: - 아래 매핑을 응답 상단에 표로 강제 탑재하고 본문에도 변환된 한글을 사용하십시오. - 리포지토리 ➔ 프로젝트 폴더 - 커밋 ➔ 변경 내용 저장 - 푸시 ➔ 인터넷에 올리기 - 브랜치 ➔ 작업 공간 복사본 - PR (Pull Request) ➔ 코드 검토 요청 - 머지 ➔ 합치기 3. **출력 스키마 규칙**: - 각 장의 첫줄에는 반드시 [🎯 학습 목표] 블록을 포함해야 합니다. - 확실한 사실이 아니거나 입력 데이터가 없으면 자의적으로 지어내지 말고 반드시 **[⚠️ 확인 필요]** 섹션을 두어 근거 부족을 알리십시오.

💡 안전장치 Few-shot 예시 4 (확인 필요 항목 명시)

Few-shot Example 4
**[입력]** GitHub 리포지토리 설정 가이드를 만들어줘. 보안 설정(토큰 사용법)이랑 사내 협업 규정 정보도 포함해줘. 대신 확실한 내용만 알려줘. **[출력]** 📘 GitHub 리포지토리 설정 및 보안 가이드 [목차] 1. GitHub 보안의 기초: 왜 중요할까요? 2. 안전한 접속 방식 (PAT 토큰 사용법) 3. ⚠️ 확인 필요 (근거 부족 항목) 4. 마치며 [상세 및 안전 조치] - 보안 설정: PAT(개인 액세스 토큰)의 생성 및 권한 설정 범위를 명확히 안내합니다. - ⚠️ 확인 필요 (근거 부족 항목): - 사내 협업 규정: 제공된 입력 정보에는 구체적인 사내 협업 정책(예: 브랜치 보호 규칙, 최소 승인 인원 등)이 누락되어 있습니다. 이 부분은 사내 보안 가이드라인(Wiki 등)을 참조하여 추가 검증 후 보강해야 합니다.

🛠️ 설계 근거 (모델 검증 연동)

실제 테스트 중 외부 데이터가 차단된 질문을 받았을 때, **GPT-5(모델 A)**와 **Claude(모델 B)**가 환각을 생성하지 않고 안전하게 거절한 실제 사례를 바탕으로 본 Few-shot 예시 4를 고안해 규칙으로 연계했습니다.
